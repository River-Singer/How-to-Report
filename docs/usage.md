# 使用两个内容 Skill

提供已有材料、已知的汇报对象和场景，以及当前想解决的问题即可。未确定目标时可先讨论；明确目标时直接说；仅需局部修改时明确范围。不要为调用Skill先编一份自己也不确定的目标表。

创建或梳理：

> 请用 how-to-report。我要在[场合]向[对象]汇报，材料是[路径]。我想解决[已知问题]。请给出具体建议页数、页序和每页可直接使用的内容，保存为[输出位置]/汇报方案.md。对会改变主线的重要未知再向我确认。

局部修改：

> 请只修改[文件/段落]中的[问题]，保留其余主线和事实。

独立审计：

> 请用 report-audit，先读[实际稿件]，再结合[要求与原资料]审查。指出有依据的问题、影响和修复方向；仅审计，不覆盖原件。

完整材料默认交付一份`汇报方案.md`。开头简短说明本次主材料共几页、讲述顺序；封面和结束页若采用则计入，备查页单列。随后逐页给出标题和可直接使用的正文、必要数据与条件。它应当足以交给用户或下游制作，不是只有讲稿，也不是“第1页讲背景”式空大纲。可参考[完整合成示例](../skills/how-to-report/assets/examples/report-proposal.md)：结合听众已知内容，交付两页具体正文；页数由这组输入决定。

给汇报者的安排与给听众的正文分别呈现，来源和未决事项按需附上；不会创建HTML、图形或前端工程。若只要口头稿、独立阅读稿或先讨论思路，直接说明即可，Skill按该形式交付，不强行分页。只改一句话或一页时，给出可直接替换的结果；增删或合并页面时同步页数和页序。已有文件名可以沿用，无需另存一份同内容的当前稿。

两包整体复制即可分别使用；真实材料与输出在安装目录之外。文件/计算/结构工具按任务需要使用，短任务不要求Run或Python。重要数值仍应有实际复核；没有工具或材料时说明具体未完成项，不补造结果。

领域知识需要适用授权，同范围已有授权不反复询问。离线方法不能代替真实项目事实。用户画像只保存显式确认的偏好与经历，本次指令优先。

## 持续修改与文件组织

继续在同一会话指出“只改第2页”“补充了新数据”或“改为给首次参会者讲”，Skill沿用仍适用的目标和内容，按影响修改。新事实联动相关标题和结尾；局部措辞不无故重排全篇。历史审计结论不能自动转成新版通过。

默认只需一个文件：

```text
本次汇报/
└─ 汇报方案.md
```

复杂续接时按需增加`工作记录.md`；独立审计放`审计/`，被审版本或重要交付留在`历史/`。不提前创建空文件。已经登记或被审计绑定的版本保留原字节，新内容另存或登记新版本；审计引用可复取的准确版本。Run是可选的另一种记录契约，采用后沿用其布局，不再维护重复状态。

《汇报方案.md》先有简短安排，再有第1页至第N页的全部内容，末尾按需列待确认与来源。真正影响判断的条件留在页面正文，工作记录不保存模型私有思维过程。先分析可只交`汇报思路.md`；用户明确另要演讲稿才增加第二份交付。换会话时提供最新采用的文件及必要已确认要求，不能依赖宿主自动恢复全部历史。

内容不清楚时，可直接指出读完还不知道什么，例如“我看懂了模块名，但不知道业务人员怎样用”。Skill按困难重组实际内容；不会要求你先学会一套写作术语。局部修改直接交替换结果，示范和研究说明不例行混入听众正文。

## 需要时使用子代理

可以直接说：“材料较多，如果当前环境支持子代理，请把相互独立的问题并行处理，再由你统一取舍和成稿。”Skill按实际能力执行，无工具仍可串行。主代理保留当前稿和用户沟通，子代理返回与自己问题相关的结论、依据及未决事项；不会让用户分别管理几份相互冲突的报告。

并行不改变来源权限与当前任务范围，也不自动产生独立审计。若需要独立审计，使用未接触作者设计答案的独立上下文，并遵守先成稿后来源/设计的读取顺序；实际暴露情况如实说明。
