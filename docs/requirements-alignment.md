## 1. 产品目标

How-to-Report 帮助宿主 Agent 根据真实受众、正式目标、场景、时长和材料，发现值得讲的内容，形成证据相称、逻辑紧密、结构丰富的汇报。相同材料可以产生不同方案。

核心价值包括两项相互约束的能力：发现原材料尚未直接说出的有用关系与论点；验证这些候选判断，收敛到适合本次沟通的内容。评估时既检查过度解释，也检查重要价值和证明义务的遗漏。

产品形态保持两个独立入口的 Skill：`how-to-report` 与 `report-audit`。内部是多 Graph 协作架构，保留候选假设、证据/论证/证明义务、任务、内容蓝图、叙事/页面及版本依赖各自的职责。方法按当前工作缺口加载，宿主负责真实工具与任务执行。研究中的概念、流程图和公式不是要求逐一建立文件、固定字段、独立 Skill 或执行节点。具体边界见[多图架构](architecture.md)。

## 4. 从完整对话补回的需求

### 4.1 用户先确认简洁的策略结构

依据第 2 轮：用户不了解该讲什么时，先从材料提取已知条件，少量追问会改变方案的关键未知，再用简洁思维导图或流程图展示候选汇报结构。

该图应表达中心问题/主张、模块顺序与关系、重点、关键缺口，以及已知时长下的分配建议。它是可讨论的策略产物；详细 Blueprint 保留证据与论证。用户不必先读长篇 Markdown 才能决定方向。

用户修改主线后，应检查受影响的证据、内容、叙事与时间分配；不需要重新确认无关的低风险表达调整。已经明确主线或仅要求局部修改时，可沿用已有决定。

新增追踪项 **FR-23：可视化策略确认**（补充原 FR-04 / FR-08）：未知方向场景可交付可读结构图；假设、重要缺口明确；用户反馈能改变相关方案；不将该图变成所有任务必经的繁琐审批。

### 4.2 V1 轻量用户画像

依据第 11 轮与本轮 DEC-07：

- 独立于 Agent Memory、Skill 指令和当前 Run 保存。
- 正式条目只记录用户确认的偏好与经历，并保留来源及适用范围。
- 用户能够查看与修正；新要求与旧偏好冲突时，以当前要求为准。
- 临时选择不自动推广为永久偏好，模型推测不自动成为画像事实。
- V1 不实现跨任务自动采集、持续后台观察或自动人格分析。

新增追踪项 **FR-22：轻量画像**：保存/读取/查看/修正可验证；当前指令覆盖历史偏好；未经确认的推测不进入正式条目；非汇报任务不触发自动更新。

### 4.3 洞察、价值与受众的实际边界

- 第 1、8、13～19 轮：方法应帮助发现未知论点、形成新表示、检验关系和收敛内容，不能只整理现有大纲，也不能把已知案例答案写进 Skill。
- 第 6～7 轮：受众理解包含知识背景、决策角色和共同问题；“某类领导必然偏好某种讲法”只能是需要结合上下文检验的判断。
- 第 23 轮：发散后必须形成可审阅的结构化内容，不能从探索直接跳到漂亮页面。
- 第 25 轮：对重大提效、降本、增收主张主动反推证据；说明缺什么、为何需要、拿不到时还能怎样诚实表达。
- 第 27 轮：助手纠正了“外部比赛应默认业务价值优先”的假设。正式评分、证据与用户选择共同决定主线；没有已兑现 ROI 不等于项目没有可讨论的阶段意义。
- 第 28 轮：价值探索是可跨阶段使用的方法，不是填满“个人/领导/部门/公司价值”的固定表格。正式目标、沟通可能产生的效果、用户个人诉求应区分。

只按实际需求与宿主能力启用复杂并发、统计建模、双语、视频、交互钻取及 PPTX 导出。V1 不自建完整 Agent 平台、全行业百科、完整 Office 引擎、全图表库或跨任务画像观察系统。

第22轮曾明确提及复用翻译等旧HTML机制；交付PRD将双语、讲稿、媒体等列为P1，未将旧版编辑/保存完整迁移列为V1必做。本补充保留这个范围差异，不把“复用运行机制”描述为原版所有功能均已承诺或完成；实施时依实际任务启用，并明确交付范围。

## 6. 需要在 M0 解决的工程问题

这些属于实现收敛，不要求用户重新选择已确认的产品方向。

1. 统一示意文档中的实体名、关系方向、来源字段、版本与可信状态；给出最小有效和无效样例。
2. 定义核心方法与可选 Knowledge 的边界、授权范围及可观察读取事件。
3. 定义画像和 Run 的独立边界、存储位置与修正语义；个人画像默认不作为仓库共享样例。
4. 明确真实宿主能力与支持声明；本地通过不能作为云端兼容证明。
5. 固定基线条件、输入资料、判定方式、失败状态和评测数据划分。
6. 确定已授权最小图表/计算适配，核验官方文档后再锁定库与版本；本轮不凭历史链接选型。

## 7. 评测与原型的已知缺口

- 25 个案例和 7 份 fixtures 属于设计输入；校验器通过只证明目录结构与引用存在。
- 独立 eval 包与交付包 reference 的 11 份对应文件完全相同；应形成单一维护源。
- 原蓝图“四个 fixture”的描述过期；正式 Dev/Holdout 划分和冻结清单尚未建立。已读开发题不能充当未见盲测。
- 需要补足多轮新数据版本导致下游失效/局部重算、HTML 局部修改的原始产物、独立计算审计的待审结果、多图同屏的实际数值输入。
- 成本分解的 oracle 需要声明交互项分配约定，不能将同样正确的另一种分解判错。
- 原型会把部分缺失或非法数值转为 0，英文排名标签还可能被裁成相同文本；不能原样承接为正式图表合同。
- 既有静态审计不覆盖真实页面容量、全部数据类型、事实真实性或语义误导；浏览器几何检查与截图阅读仍需执行。
- 新增画像与策略图需求需要补对应行为回归；洞察评价同时检验遗漏、重复、无关扩展和证据越界。

## 11. 0.4.0用户追加的可观察认知关口

既有目标发现、候选区分和交互方法继续保留，本次进一步要求：大纲前看候选结果是否改变证据/结构/结尾；先读材料，再作少量非引导澄清，已确定目标不反复问。主体按人/组织的理解、判断、动作及权责理解，项目不拟人，不默认冲突、展示能力或恢复旧计划。否定的个人诉求不在后续暗中优化。

新方向须说明独立问题、可区分观察及判断/行动差异；可以用旧表示相同而新方向不同的假设情境作工作判据，但不把假设当事实或数学独立性证明。反命题通常是同问题的竞争答案；相关但决策含义不同的指标应保留，并检查依赖交互。候选数量是可调起点，重要缺口继续、同义合并、事实不足请求证据，预算停止需保留未解和未探索范围。

这些要求已进入共享运行方法与审计方法；是否在真实模型交互中奏效，交由本次分阶段探针观察，尚无新版行为结果。

## 12. 0.4.0页面表达的原型对齐

页面能力以早期Visual-Lab原型的可组合分析结构为参照，允许层级、排名、趋势或矩阵与辅助证据在同页形成主辅关系；不能把需求缩为四种整页卡片模板。新增有界递归空间组合、文字/层级/指标及条形/折线/矩阵，保留简单计划。浅蓝白、标题层次和主辅比重是表达约束，空间关系不能替代证据与业务关系。图表缺数仍缺失，不为视觉演示造数。最终实际浏览器和工程检查完成后再冻结模型测试包；旧基线检查不自动覆盖此扩展。
