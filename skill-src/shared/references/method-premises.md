# 前提与约束审查

方法修订：0.9.0（2026-11-12）。

- **触发**：建议依赖尚未核实的前提、方案与目标混淆，或症状解释遗漏真正制约条件。
- **动作**：区分已知事实、用户目标、不可擅改的合同/审批/资源边界和工作假设。将具体困难抽象为需要满足的条件，再改变一个可变前提比较后果。硬约束只能标出或建议另行变更，不以“第一性原理”取消。
- **可观察结果**：写明哪项前提有证、未知或被反例挑战；替代前提会改变哪项方案/证据需求。增加人力与取得接口批准可能解除不同阻碍，不能自动互换。
- **回落与停止**：回到原材料，指出应改的建议或最小补件。若抽象没有新增区分、前提已明确，或差别只能靠事实核实，停止继续升维。
- **需挑战的地方**：核对抽象有没有丢掉时间、授权、对象和必要条件；候选前提不能写成项目事实，合理替代不等于用户已选择。已明确目标不反复问动机。

背景：[本地抽象与纠错研究摘要](method-sources/sources/step-back.txt)。研究任务与管理汇报不同，不能据论文标题声称本 Skill 已提高推理正确率。

本卡交回一个可用区别、修正判断或具体待核事项；不另启动成稿/验收流程。共用[含义保真标准](semantic-structuring.md#含义保真的共同标准)。

## 把操作落回判断

必要输入：已确认目的与真实角色、本次请求、支持依据、已知限制和重要不利材料；不要仅用主Agent摘要替代可读原资料。

对能阻断本场目的的一条关键前提，先承认已成立的支持，识别尚需哪种事实或逻辑连接，检查什么证据会使异议失效。必要条件不等于充分条件，击破一个次要理由后仍须看其他依据是否足够。上层目的已有效确认时不无限反问，除非相关新证据改变其适用。

合成例：“金额有余额，所以这项支用可以批准”缺用途/授权条件；核已有批准记录后若覆盖该用途，撤回这条异议。误用：为坚持反对再换不相关理由，或把想象的一次失败写成真实风险事件。 以上为合成教学例。

主Agent先用已有资料完成可做的分析，真正缺事实时说明具体最小输入/替代、它决定哪个判断和不补时的边界；不是让用户完成分析。所缺若为工具或专业能力，明示尚未完成的核验，不伪称只缺资料。产物是有依据的区别、判断或未决条件，落实到实际内容后停止。

挑战者只用方法形成目标相关问句；不把本卡操作清单或修复建议交给主Agent。审计仍检查依据、影响和修法；真实委派见[契约](agent-delegation.md)。
