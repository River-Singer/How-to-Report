# PPT视觉组织与形状组合

本方法接在页面任务、证据与理解路线之后，用可见关系组织内容，并在实际成图中复验。设计目标是让听众更快辨认重点、分组和关系；增加色块、曲线、阴影或图标的数量本身不构成改善。沿当前主题控制字体、颜色、线宽和间距，不把参考公司的品牌外观当成规则。

## 从信息关系选择视觉语法

| 听众需要看出的关系 | 可采用的组织方式 | 必须避免的误读 |
|---|---|---|
| 同属一个主题、下有不同细节 | 共享区域、左侧轨道、标题下短线；组内近、组间远 | 给每句话套相同边框，使父组和子项同权 |
| 时间先后、步骤推进 | 一条连续基线及明确节点；只有方向有意义时才用箭头 | 等距表示真实时长，或把并列能力串成因果 |
| 共同基础支撑多个模块 | 跨列的共享带、清晰的上下层、必要的依赖连接 | 只将“共享平台”写在旁边，归属仍靠读者猜 |
| 并列选项、相同角色的指标 | 共用对齐线、同图种、同尺寸与标注顺序 | 给同类值任意大小、形状、颜色，制造不存在的差别 |
| 主判断和支持证据 | 有主次的列宽/跨列范围、角色字阶、局部强调 | 所有区块同样大、同样深色，或用大图挤压证据 |
| 循环及循环各阶段的说明 | 可追踪的闭合方向；阶段标识在图内外一致 | 大环只承担装饰；图旁解释无法对应到阶段 |
| 层级、输入与输出 | 分层区域与有依据的连线，主节点和附属节点分级 | 把所有对象画成单条流水线，丢掉汇聚或分叉 |
| 必须逐项查阅的明细 | 稳定行列、对齐和轻分隔，突出检索入口 | 用装饰图形破坏查找；要解释分布时又只交数字表 |

一页可组合几种关系，但每种视觉记号保持含义稳定。正文通常14pt、最小角色9pt；正文80%黑、次要注释30–40%黑沿全局tokens，关键分母和限定不得降成难读灰字。同类比例采用统一语言，保留各自分母；独立单值和超100%的参考比值不能为了统一变成完成率环图。新稿优先纯色，渐变保持最低偏好。

当前默认偏好为内敛的 `report-default`：深蓝、蓝、青绿和灰蓝建立层次。用户随后确认更喜欢这组配色，公开主展示沿此偏好；`consulting-spectrum` 的草绿、青蓝、深蓝、中性灰、橘色和红色保留为第六套可选色卡，不自动替换默认。按稳定的主题、阶段或系列角色分配颜色，不要求每页用全套。橘色可少量承担重点，红色若表达风险须有对应事实，不能让普通分类被误读为告警。正文仍为80%黑，当前注释角色35%黑；换色卡不连带改成彩色正文。颜色还须配合标签或位置辨认关系，不能靠“颜色更多”证明美观。新旧形态对照使用同一全局色卡，配色偏好的核验另行说明。

## 用户指定参考时，先确认要保留的构形

参考既可能指定信息结构，也可能指定形状如何构成视觉整体。将用户已明确的形态意图写进当前设计取舍：例如“厚实弯曲箭头首尾衔接，阶段本身组成循环”，就不仅是“有四节点、四条有向边”。四个矩形加细线即使拓扑正确、文字无重叠，也没有满足这一构形要求；不能用功能关系通过抵消明显的原型感。

先打开库中最匹配的已有variant完整预览及参数合同，实际比较构形、方向、节点数量和标签容量，记录采用或舍弃的原因。不能只搜到名字含cycle的组件就停止；确实没有匹配能力时指出缺口，由engine实现参数variant，不能由AI临时手画最终路径，也不能称线框替代已达到指定参考效果。

对这种循环，实际成图应看到：各段厚度和曲率形成连贯的整体，箭头方向清晰；阶段形状与循环路径共同成型，段间间隙有一致节奏；标签处于可读安全区，不挤进尖端、收窄处或相邻段；图外说明与阶段标识、色义一致。文字可水平放置或移到外侧并建立明确对应，不强制复制品牌、图标和旋转文字。不得为模仿轮廓缩字、截断名称或删解释。

厚箭头循环适合阶段数受控、标签简短、强调周而复始的关系。长标签、多分叉、跨阶段依赖或需要逐项展开时，仍应比较外置说明、其他已有结构或分区方案；不是所有闭环都改成厚箭头。偏离用户指定构形要给当前内容与实际试排的理由，不能用笼统的“更简洁”替代。构形匹配、关系正确和真实可读分别验收。

## 八项设计决策

1. **先定视觉入口。** 标题下的第一眼应落在本页最重要的判断、主图或关系，而不是最大装饰。用同角色字阶、可解释的面积差和有限强调形成顺序；不要把全部文字加粗。
2. **让分区表达归属。** 优先用共同对齐、间距和共享区域。只在边界不清时增加线或底色；可以用一条轨道连同组条目，不必每个条目一个卡片。改变边框但未改变分组可读性不算结构改进。
3. **让线承担明确工作。** 线可作分隔、基线、时间轴或连接，四者不能混用。关系线必须有明确源、目标和含义；顺序关系要能连续追踪，普通并列不自动加箭头。
4. **用重复建立节奏，用差异表达主次。** 同级标题起始边、图表大小、内距及标签顺序一致。需要突出一个重点时，改变它的占位或强调角色，其他同类仍保持统一。视觉平衡不等于左右机械对称。
5. **形状组合保持可读。** 背层区域承载归属，中层线承载关系，前层节点与文字承载内容。用覆盖制造连接效果时，检查线是否在正确端口出现，文字和有效数据不能被盖住。白块遮盖、裁切、布尔求差是不同机制，不能互相冒充。
6. **把内容框和可见边界分开考虑。** 描边、端帽、阴影和凸出装饰可能越过名义frame。容器内距须预留给轨道和边线，最终成图还要检查边缘与邻项。禁止靠遮挡隐藏超出容量的文字。
7. **留白用于断句。** 组间空隙标出层级和转场；组内空隙保持关联。内容稀少时先缩小无意义拓扑、共享标签、试更紧凑栅格。内容诊断的占用率是线索，不能靠放大图形、加无关配图或塞文字提高指标。
8. **保留关系后再减页。** 合页前复验论证和顺序，再用固定字号测排。对全稿继续挑战能否少一页，不能以“高级感需要留白”跳过。阅读关系不同也不必天然分成两页；真实试排和必要承接决定取舍。

## 从Figma、Canvas和形状编辑器借鉴什么

- Figma把尺寸与内容约束放在容器上，grid轨道能承载跨格对象；视觉栅格线和自动布局是两回事。对本项目的启示是保存布局树和数量约束，内容变动重新测排，不能只保存最终坐标。[Auto layout](https://help.figma.com/hc/en-us/articles/360040451373-Guide-to-auto-layout-in-Figma)、[Grid flow](https://help.figma.com/hc/en-us/articles/31289469907863-Use-the-grid-auto-layout-flow)。
- Canvas的状态作用域包含变换、裁切和绘制样式；裁切会收紧当前可见区域，合成模式决定像素如何覆盖。对本项目的启示是组件内样式与层序有边界，不能让前一个组件的状态泄漏到后一个，也不能把像素合成结果称为可编辑PPT路径。[Save](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/save)、[Clip](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/clip)、[Compositing](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/globalCompositeOperation)。
- Konva以父容器中的子节点次序绘制；普通分组与独立合成组不是一回事。对本项目的启示是按稳定树序安排区域、连接和节点，不把局部层序当成任意全局z-index。[Konva zIndex](https://konvajs.org/docs/groups_and_layers/zIndex.html)。
- Figma、Photoshop的路径并/差/交/排除改变的是几何；覆盖只改变可见先后。Photoshop描边位置和效果缩放还说明外观尺寸不能只看原始路径。对本项目的启示是把几何、样式、绘制次序分开，所需能力不足时明确报出，不能凭遮盖宣称已实现布尔运算。[Figma Boolean](https://help.figma.com/hc/en-us/articles/360039957534-Boolean-operations)、[Photoshop path](https://helpx.adobe.com/photoshop/desktop/draw-shapes-paths/create-shapes/manage-path-components.html)、[Layer effects](https://helpx.adobe.com/photoshop/desktop/create-manage-layers/apply-layer-effects/layer-style-effects-and-options-overview.html)。
- PhotoCraft公开架构保留live-shape参数再生成路径，并把路径操作与烘焙分开；命令注册表共供多入口。这提供参数化与可重放的实现思路，不代表取得Photoshop专有内核，也不等于本PPT引擎已支持其全部能力。[PhotoCraft](https://github.com/storytold/photocraft)。

这些是可核查的公开机制与项目迁移判断，不能统称“逆向了Figma/Photoshop”。布局计算、路径计算和渲染结果需要各自的证据。

## 本项目的调用边界

先辨认取用资产的用途。**原生保真素材**以原样配置、形状和图层重建为验收，保留原件，不为统一美化覆盖源样式；换色或重组另存派生。**结构技术样例**展示参数、布局或关系能力，含占位词、基础盒子或细线并不自动构成缺陷，但不能当作已经完成设计的成稿。**面向成稿的设计组合**需兼顾实际内容、层级、构形、节奏和文字安全区；同一个基础组件可被不同组合使用。

制作成稿时，在业务语义和容量匹配的前提下，实际检索并打开相关设计组合候选，再比较基础模板与组合的阅读效果。不能因为基础原型可执行就结束选型，也不能仅凭recipe名字、推荐标签或所谓成熟度分数直接采用。阶段带、分层平台、并列解释等共享组合应有明确场景和输入约束；新能力是否已注册、可检索且可执行须查本版入口。已有简洁表格、阅读分栏与比例图若已适配其任务，无需强加装饰。未实际优化的模板仍按原用途和原检查范围说明，少量新组合不等于全库已完成UIUX升级。

采用实际已注册组件、参数模板与当前布局合同。固定列grid的直接子项可用`column_span`表达跨列，共享区域可用容器surface的`rail`、`rule`、`bracket`强调，row/column的`connect=sequence`表达显式相邻顺序；最终几何由computed入口计算。这些能力只解决所声明的局部关系：不包含跨行、subgrid、任意自动绕障、多方向图路由或完整布尔系统；`auto_fit`与显式跨列的组合不支持。具体字段、适用子节点和限制以本版布局合同为准，不能照搬Figma接口名。

复杂循环、曲线轨道或多层关系先查已有拓扑/参数模板。现成组件不具备需要的关系时，可沿授权采用可读原图，或提出具体引擎能力缺口；不要用“美化”名义让AI写最终坐标或自由路径。复制原文件的原样重放、换成自有tokens的派生模板、内容变化后的动态重排是三项不同验收。

## 如何证明改善

对有实质设计争议的页面做一次同内容、同tokens、同字号、同画布的前后对照。保留全部叶文本、数据、图片身份和关系，记录改变的容器/组合。先验证几何及内容不丢失，再实际看图回答：重点是否更早被识别、分组是否更清楚、关系是否更容易追踪、同类是否一致、是否增加无意义装饰。只改颜色不能证明自动排版更好；删减内容、缩字或增大画布不能冒充改善。

算法可核尺寸、对齐偏差、间距、越界、重叠、层序、主题角色与已声明关系；它们是可检测代理量。重点是否恰当、分区是否符合意思、读序是否自然、图形是否误导以及整体是否舒适，仍须独立查看当前成图判断。不把对象数、颜色数、信息占用率加权成“审美总分”。审计与具体问题的处置沿[ppt-visual-review](ppt-visual-review.md)。
